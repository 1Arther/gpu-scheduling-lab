类型的识别与建模，导致任务类型与设备能力不匹配，进而影响整体性能与资源效率。本设计聚焦异构 vGPU 集群中的调度优化问题，提出一套基于“GPU 类型自动识别”的调度增强方案。核心思想是采集各型号 GPU 的公开规格与驱动层可读静态特征（FP16/INT8、显存容量/带宽、SM/TensorCore 等），构建统一的能力向量；采用无监督聚类自动归纳 GPU 类型簇，并将簇结果映射为 Training / Inference / Balanced 类型标签，为调度提供可计算的资源类型先验。在此基础上，调度器在 Kubernetes 环境中以插件形式实现，结合作业标签与 GPU 类型标签进行适配分配，同时支持公平性评分机制与调度排序优化。为后续异构 vGPU 集群调度策略的实现与验证提供设计基础。关 键 词关键词数量三至五个，主题词之间空一格（英文用“ / vGPU、阿里云vGPU）已实现对显存、算力、缓存等核心资源的精细化管控，通过硬件辅助虚拟化与软件隔离机制，有效规避了不同任务间的资源竞争与干扰。以HAMi为例，其支持基于QoS的算力分配策略，可根据任务优先级动态调整vGPU实例的算力占比，同时提供显存页表隔离、地址空间保护等功能，确保多租户任务的运行稳定性。实践数据表明，引入vGPU技术后，物理GPU资源利用率可从传统独占模式的30%-40%提升至60%-80%，大幅降低了算力集群的部署与运维成本，为云原生AI算力服务的规模化推广奠定了技术基础[2]。然而，在实际工程部署中，异构GPU集群环境下的调度优化问题逐渐成为制约算力效能释放的核心瓶颈。当前主流算力集群普遍存在“硬件异构化、任务多样化、租户多元化”的特征：硬件层面，集群中往往混布不同型号、不同代际的GPU设备（如NVIDIA A100、Tesla V100、RTX 3090、H100），其算力输出、显存带宽、TensorCore支持度、精度计算能力等核心指标差异显著（例如H100的FP8算力是A100的3倍以上，显存带宽提升约50%）；任务层面，既有需海量显存支撑的千亿参数模型训练任务，也有对延迟敏感的实时推理任务，还有算力需求适中的中等规模微调任务，不同任务的资源需求呈现显著异质性；租户层面，多用户共享集群资源，不同租户的任务优先级、运行时长、资源诉求存在较大差异。传统调度策略（如FCFS、SJF、HRRN）多基于“资源同质性”假设设计，仅关注任务到达时间、预估运行时长等单一维度信息，缺乏对GPU硬件异构特性、vGPU实例性能差异及任务资源需求匹配度的精准感知，极易引发“资源错配”问题。具体而言，资源错配主要体现在两个方面：一是“大材小用”，即高价值GPU资源被低需求任务占用，例如将仅需基础算力的INT8量化推理任务调度至具备超强训练性能的A100 vGPU实例，导致高算力资源利用率不足，造成算力浪费；二是“小材大用”，即高需求任务被分配至低性能vGPU实例，例如将显存需求16GB的BERT-Large模型训练任务调度至仅配置8GB显存的V100 vGPU实例，直接导致任务因显存不足（OOM）终止，或被迫降低批次大小（batch size），使得训练效率下降30%-50%。在多租户混合作业场景中，这种错配问题进一步放大：训练任务与推理任务抢占资源、长时任务与短时任务相互干扰，最终导致集群整体吞吐量降低、任务平均延迟升高、GPU资源利用率不均衡等一系列问题。因此，如何构建具备动态性能感知能力的调度机制，精准匹配任务需求与vGPU资源能力，实现“对的任务用对的GPU”，已成为云原生AI算力平台亟需解决的核心技术难题。本研究提出通过性能采集实现vGPU性能画像与类型分类，为调度决策提供精准的资源能力参考，有望从根源上改善传统调度器对异构资源“视而不见”的局面，大幅提升任务-资源匹配精度。与此同时，多租户GPU集群的调度优化还面临“效率与公平性”的双重权衡难题，这一问题在无抢占式调度环境中尤为突出。一方面，不同租户的任务存在显著差异：部分租户的任务为长时运行的大规模训练作业（运行时长可达数天甚至数周），部分租户的任务为短时高频的推理作业（运行时长仅为数秒或数分钟），若缺乏有效的公平性保障机制，长时任务可能持续占用核心GPU资源，导致短时任务长时间等待，形成“饥饿现象”；极端情况下，个别租户的任务可能占据集群80%以上的GPU资源，严重损害其他租户的合法权益，违背多租户环境下的资源共享原则。另一方面，集群管理者需确保GPU资源始终处于高效利用状态，避免因过度追求公平性而导致资源闲置，影响集群整体吞吐量。传统公平性调度方案（如基于租户配额的静态分配、轮询调度）虽能在一定程度上缓解公平性问题，但缺乏对任务动态特征、资源实时状态的自适应调整能力，难以平衡“个体公平”与“整体效率”。针对这一困境，本课题引入经典的最高响应比优先（HRRN）模型作为基础调度框架，通过“响应比=（等待时间+估计运行时间）/估计运行时间”的核心逻辑，平衡长时任务与短时任务的调度优先级，缓解任务饥饿问题；同时，创新融合强化学习（PPO）算法，构建具备自适应学习能力的调度策略，通过实时采集集群运行数据（如任务等待时间、节点负载、资源利用率），动态调整调度因子权重，实现公平性与效率的最优平衡。本研究将通过对比实验验证强化学习增强型HRRN策略相较于传统队列调度策略的优势，重点量化其在任务平均等待时间、饥饿任务比例、Jain公平性指数等核心指标上的提升效果。这一研究方向不仅具备重要的理论价值，更贴合实际工程需求——公平且高效的资源分配能够提升租户满意度，减少因资源争夺引发的运维纠纷，同时最大化集群算力产出，实现“个体公平”与“整体高效”的双赢。本课题的研究成果具有明确的工程落地场景与实用价值，计划在新华三集团自主研发的“傲飞”（Ampha）智算平台上进行实践验证与成果转化。Ampha智算平台是新华三面向AI与HPC融合场景打造的一体化算力管理平台，基于Kubernetes与Slurm调度框架构建，具备多用户统一身份认证、存储资源池化、精细化计费、全链路监控等核心功能，可实现AI训练作业、传统HPC作业及大数据处理作业的统一调度与管理，已广泛应用于互联网、金融、科研院所、智能制造等多个行业。当前，Ampha平台的GPU调度模块仍以传统策略为主，在异构vGPU环境适配、多租户公平性保障等方面存在优化空间。本研究开发的具备vGPU性能感知与公平性保障的智能调度插件，可无缝集成至Ampha平台的调度框架中，通过精准的vGPU类型分类、动态的调度优先级校准，充分挖掘异构GPU集群的算力潜能，预计可使任务平均完成效率提升20%以上，GPU资源利用率提升15%-25%，同时将饥饿任务比例降低30%以上。这不仅能够直接提升新华三Ampha平台的产品竞争力，为客户提供更高效、更公平的算力服务，还能为业界异构vGPU集群调度优化提供可复制、可推广的技术方案与工程范例，推动云原生AI算力调度技术的标准化与产业化发展。二、国内外研究概况与发展趋势1.异构GPU调度的关键挑战当前 GPU 集群调度面临多方面的挑战，其中最突出的问题包括 资源碎片、作业排队公平性和跨节点调度开销等。资源碎片问题： 在引入 vGPU 共享机制后，多任务在同一 GPU 上运行可能造成显存和算力碎片化。例如，一个 40GB 显存的 GPU 被切分运行多个小任务后，可能残留无法充分利用的碎片显存，导致新的作业因显存不足而无法调度，即使集群中仍有碎片资源空闲。大型云服务商的生产实践表明，细粒度划分 GPU 资源会带来严重的碎片：数百块 GPU 因部分显存被占用而整体上无法再被分配给新任务。传统的资源打包算法难以解决这一问题，因为GPU共享打破了经典装箱模型的假设。近期有研究专门定义了衡量 GPU 碎片程度的指标，并提出碎片梯度下降（Fragmentation Gradient Descent, FGD）策略，旨在将任务调度到能够 最小化碎片增量 的位置，从而最大化可用 GPU 数量[21]。实验显示，与贪心打包策略相比，FGD 可减少多达 49% 的未利用 GPU，显著降低了碎片造成的资源浪费[11]。由此可见，碎片问题是 vGPU 调度中亟需关注的重点之一，解决方案需要在任务放置时统筹考虑显存利用的全局优化。任务队列公平性： 公平调度意味着不同用户或不同作业应在等待时间和资源分配上受到公正对待。然而，深度学习训练作业往往持续时间长、资源需求大，如果仅追求吞吐量最大化，调度器可能倾向于一直调度大型作业，从而造成短作业长期得不到资源（饿死）。传统大数据和 HPC 调度采用的很多公平原则（如 max-min 公平、Dominant Resource Fairness 等）在 GPU 工作负载下并不完全适用。为此，学术界提出了多种新的公平衡量指标和策略：例如，Mahajan 等人在 NSDI 2020 提出的 Themis 框架引入“完成时间公平”指标，要求所有作业相对于各自独占运行时的完成时间达到均衡[1]。Themis 采用两级调度架构，由作业对资源进行竞价，中央信元通过拍卖机制分配 GPU，在短期内适度牺牲局部公平以换取效率，但从长期确保整体完成时间的公平。实验证明 Themis 在提高公平性的同时，能保持较高的集群效率。又如 Ye 等人在 TPDS 2021 提出的 Astraea 调度器，关注多租户环境下长期 GPU 时间公平性（Long-Term GPU-time Fairness），通过度量各租户实际获得的累积GPU时间占比来指导调度决策[25]。这些工作表明，在 GPU 集群中保障公平需要引入新策略，例如拍卖机制、积分机制或长周期度量，以平衡不同时间尺度上的公平需求[13]。值得注意的是，在异构GPU环境中，公平性问题更为复杂：用户往往都倾向获取最新最强的GPU，使得旧型号 GPU 被视为次等资源。为此，一些研究尝试通过异构 GPU 时间换算来实现公平，例如早期的 Gandiva-fair 调度器允许用户在不同性能GPU上透明地交易 GPU 时间，以确保即使分配到较慢GPU也能通过获取更多运行时间来补偿，从而维持用户间公平[15]。总的来看，公平调度仍是GPU集群管理的核心挑战，需要综合考虑任务的历史等待、所获服务时间以及GPU硬件差异等因素来做出更智能的决策。跨节点调度开销： GPU 集群通常包含成百上千节点，调度器在全局范围内为新作业选择节点和GPU需要一定的计算和通信开销。随着调度算法复杂度提高（例如引入基于优化求解或强化学习的决策），每次调度计算可能耗时增加。此外，一些高级策略（如 Themis 的拍卖、Gavel 的全局最优化等）为了在全局范围达到最优分配，可能进行复杂的搜索或求解线性规划，当集群规模和作业数目很大时难以实时完成。例如，Stanford 提出的 Gavel 调度器尝试针对不同公平定义（如吞吐量最大化、完工时间公平等）求解全局优化问题，但研究指出对大规模数据中心而言其计算开销过高，需要通过划分集群、分而治之的方法降低复杂度。因此，如何控制调度决策的开销亦是实际工程中要考虑的因素之一。这促使研究者探索轻量高效的智能调度方法，例如利用强化学习在大量历史数据上训练出近似最优策略，以替代每次任务到来时的繁重计算[12]。值得一提的是，本课题采用的 PPO 强化学习模型属于在线决策开销小但训练阶段较长的方式：通过在仿真环境离线训练得到调度策略网络，在实际调度时仅需毫秒级推理即可给出决策，从而不会显著增加单次调度延迟，在公平性改进和系统开销之间取得平衡[8]。2.典型调度策略及其优劣为应对上述挑战，业界和学术界提出了多种调度策略和算法，涵盖从简单启发式规则到复杂优化方法。以下对几种具有代表性的策略进行比较：先到先服务（FIFO/FCFS）： 最简单的调度策略，按照作业到达顺序分配资源，是典型的队列排队策略之一。其优点是实现简单、直观，能一定程度上保证公平（先来的不会被完全饿死），但缺点是可能导致大型作业占据资源过久，阻塞后续小作业，从而增加系统平均等待时间。当存在长短作业混合时，FCFS 的效率和公平性表现往往较差，也是本课题HRRN强化学习模型的核心对比对象之一。最短作业优先（SJF）： 优先调度估计运行时间最短的作业，以期望降低平均等待时间。SJF 在作业长度分布差异较大时能够显著优化集群吞吐和响应时间，对于大量短任务场景非常有效。然而，其缺点是可能饿死长作业（长任务反复被更短的任务插队而延迟调度）。在GPU共享环境中，SJF由于不考虑资源碎片和设备差异，可能造成短任务占用高性能GPU、长任务迟迟无法启动的不公平局面。最高响应比优先（HRRN）： 综合考虑作业等待时间和服务时间的调度策略，其优先级 = (等待时间 + 运行时间) / 运行时间，即响应比。HRRN 会动态提高等待时间长的作业的优先级，从而在一定程度上避免长任务被饿死。经典 HRRN 在CPU作业调度中被证明能显著降低长任务饥饿概率。然而在细粒度 vGPU 调度场景，HRRN 的优势未必充分体现。原因在于：HRRN 的计算只基于时间维度，对底层 GPU 资源碎片结构缺乏感知，可能出现某任务响应比虽然很高但由于节点显存碎片原因依然无法被调度的情况[5]。我们的仿真分析也发现，在显存高度切分、各节点剩余碎片不均衡时，单纯依赖响应比排序不足以保证任务尽快调度。因此，本课题旨在改进 HRRN 策略的资源感知能力，构建HRRN强化学习模型，通过引入对GPU碎片和负载的感知因素，避免传统HRRN中“高响应比≠高可调度性”的尴尬局面，并将其与FIFO等队列排队策略进行对比，验证其优化效果。Dominant Resource Fairness（DRF）： 这是多资源公平分配的经典策略，最早应用于数据中心 CPU-内存等多资源调度。DRF 的思想是每个用户按其最主要资源（dominant resource）的占用比例进行公平分享，从而保证没有用户在所有资源上都占优势。应用在 GPU 集群中，DRF 可用于按用户分配 GPU 数量或 GPU 时间，确保各租户获得相对均等的加速器资源份额。DRF 的优点是有理论上的公平性保证，避免某单一用户垄断资源；但缺点是在任务层面缺乏细粒度考虑，尤其不能处理显存碎片、GPU 类型偏好等问题。此外，DRF默认假设资源可被连续分割，对于GPU这样不可进一步细分的资源（占用一块就是100%）需要结合时间片或虚拟化才能应用，这增加了实现复杂度。智能优化与学习型策略： 随着调度问题复杂度攀升，学界开始探索机器学习和优化方法来设计调度器[27]。一方面，启发式算法（如模拟退火、遗传算法、多目标优化）被用于模型化调度决策，将调度视为NP难的组合优化问题近似求解。例如 gVMP 框架将 vGPU 分配建模为多目标优化问题，综合考虑性能、能效和资源约束，并设计启发式算法求解[4]。另一方面，强化学习（RL） 逐渐成为调度领域的研究热点[12]。RL 代理可以通过与仿真环境反复交互学习调度策略，在高维状态空间中寻觅人类难以直观发现的决策模式[19]。已有工作采用 深度强化学习（如 DQN、PPO） 实现自动资源分配和容器调度，并取得比静态策略更优的性能[26]。特别地，深度学习的兴起也促使将图神经网络（GNN）引入资源调度：利用 GNN 建模集群中任务和节点构成的复杂图关系，可以更好地捕捉任务之间、任务与资源之间的依赖[27]。例如近期有研究利用 GNN 编码作业DAG与设备拓扑，以强化学习进行全局调度决策，表现出较强的泛化能力[16]。总体来看，调度算法正从静态规则迈向自适应智能：通过学习模型感知资源和任务语义、动态调整策略，被认为是提高复杂环境下调度绩效的有效途径[7]。这也代表了未来的发展趋势，即调度系统将融入更多机器学习技术，实现“按需调整”的智能调度，而本课题提出的HRRN强化学习模型正是顺应这一趋势的探索，通过与传统队列排队策略对比凸显其优势。国内研究与系统实现： 在 GPU 调度领域，国内的研究工作相对较少，但也有一些探索主要集中在GPU 共享机制和Kubernetes 调度扩展方面。例如，武汉大学提出的 GaiaGPU 和台湾学者提出的 KubeShare 系统，均实现了在容器云中对物理 GPU 进行划分共享的方法，支持在 Kubernetes 下将 GPU 视作可细分的一级调度资源。这些系统多通过设备插件或 API 转发的方式，将每块 GPU 映射为多个可供调度的虚拟设备，从而让调度器能分配半块甚至更小粒度的 GPU 给不同容器[9]。然而，这些早期方案主要关注静态的资源隔离与配额，在调度决策方面仍然使用较简单的规则，缺乏对作业异构需求或公平性的深度考量。例如，KubeShare 针对每个GPU维护一个时间片队列实现公平共享，但并未针对不同任务类型优化调度顺序；GaiaGPU 强调通过 Kubernetes 设备插件暴露切分后的 GPU，但调度阶段仍依赖默认队列排队策略。当前国内外已有的工业实现（如 NVIDIA 的 Kubernetes Device Plugin、阿里云的 GPU Share Scheduler）也大多提供了GPU 切分和基本的调度策略，但在调度智能化和公平性保障方面仍有明显不足[20]。可以说，实现一个既“懂硬件异构”又“懂多租户公平”的智能调度器，并通过与传统队列排队策略对比验证其有效性，是一个国际前沿又具有现实意义的研究方向。综合来看，异构 vGPU 集群的资源调度正逐步从静态配置走向类型识别、智能决策、公平保障与系统集成的协同优化新阶段[18]。3.主流调度平台及工程实现在云原生环境中，主流的 GPU 调度依托于 Kubernetes 生态，但需要结合插件和扩展框架来实现高级功能。目前较具代表性的有 Kubernetes 原生调度器 + Volcano + HAMi 的组合方案。Kubernetes 原生调度： Kubernetes 默认调度器能够识别节点上 GPU 数量等资源，并基于预选和优选策略为 Pod 选择节点。然而默认调度器的策略相对简单：对 GPU 不支持拆分，同一时刻一个 GPU 仅可给一个 Pod 使用；调度决策主要基于资源匹配和预留，采用简单的队列排队逻辑，并未考虑任务的等待时间或历史信息，也没有专门的公平性机制。多租户隔离通常通过命名空间配额或优先级来粗粒度控制。总的来说，原生调度在 GPU 利用率和公平性优化方面存在局限，需要扩展。Volcano 调度器： Volcano 是 CNCF 孵化的开源批处理调度系统，旨在增强 Kubernetes 在批量作业和深度学习任务场景下的调度能力[10]。它提供了作业队列、Gang调度、配额公平等机制，可支持成组任务同时调度和跨作业的资源共享控制。特别是在多租户情况下，Volcano 引入了层次化队列和公平分享策略：管理员可为不同用户或项目创建队列并设置权重配额，使调度时各队列按权分享 GPU，不会让某一队列独占资源[28]。当资源紧张时，Volcano 能确保每个队列按比例获得资源，从而实现租户间的公平。例如，在生产环境中可配置某研究组和另一组各50%配额，Volcano 会动态调整调度顺序以逼近此目标。此外，Volcano 还支持预留和抢占等高级特性（取决于配置），可以提前为即将到来的大作业预留GPU槽位，或在允许抢占的场景下暂停低优先级任务腾出资源，从工程上增加了调度的灵活性。总之，Volcano 在 Kubernetes 之上实现了对批处理AI作业的友好支持，被广泛用于 AI 训练、Big Data 等需要复杂调度策略的领域[30]。HAMi 平台： HAMi（异构 AI 计算虚拟化中间件）是近期开源的 Kubernetes GPU 虚拟化和统一调度解决方案，由社区和企业（如华为、科大讯飞等）共同支持。HAMi 原名 k8s-vGPU-scheduler，本质上扮演两个角色：一是GPU 设备插件和虚拟化引擎，负责将每台物理GPU按照配置切分成多个vGPU实例并进行硬件隔离；二是作为调度扩展（Scheduler Extender），参与 Kubernetes 的调度决策。在节点层面，HAMi 通过守护进程收集每个节点GPU的使用情况（例如剩余显存、剩余算力份额），并在调度阶段通过扩展接口提供 Filter 和 Score 功能：筛选出具有足够可用vGPU资源的节点，并按照策略为节点打分。HAMi 强调对多种异构加速卡的支持（GPU、NPU、MLU等）以及与 Kubernetes API 的无缝兼容，不需要改变用户提交作业的方式。目前 HAMi 已进入 CNCF 沙箱项目，体现了业界对GPU 虚拟化共享和拓扑感知调度的高度关注。在实际集群中，上述组件常被组合使用以发挥各自优势。例如，新华三的 AMPHA 平台即采用 “Kubernetes + Volcano + HAMi” 的架构：由 Volcano 接管 Kubernetes 的调度器，实现作业队列和全局公平调度；同时部署 HAMi 作为设备插件和调度扩展，以支持 GPU 分片和精细化的设备选择策略。具体流程是，当有新的 AI 任务提交时，Volcano 根据作业所属队列、优先级和集群当前负载决定何时调度以及将 Pod 分配到哪一节点，在此过程中 HAMi 扩展会过滤掉不满足该 Pod 显存/核心需求的节点；节点选定后，HAMi 在目标节点上按照预设策略为 Pod 挑选具体的 GPU 实例（如某块 GPU 的某个空闲vGPU槽），并完成显存及算力的隔离分配。这种分层协同的方式将宏观的公平调度（Volcano 层面）与微观的资源感知调度（HAMi 层面）结合起来，兼顾了策略灵活性和系统性能。可以认为，Volcano 解决“选哪台机器、让谁先跑”的问题，HAMi 解决“在该机器上选哪块/哪份 GPU”的问题，两者各司其职又紧密配合。随着这些平台的成熟，工程界已经具备了在生产系统中部署智能调度算法的土壤。本课题的研究成果也将立足于此技术栈，实现与 Kubernetes、Volcano、HAMi 的无缝对接，通过与基于这些平台的队列排队策略对比，在真实环境中验证HRRN强化学习模型的有效性。三、选题的先进性与实用性（1）vGPU 类型感知调度（先进性）: 本课题针对GPU 异构性缺乏感知的问题，提出基于性能采集的 vGPU 自动分类方法。通过为每种物理 GPU/虚拟GPU 运行一系列训练型和推理型子任务并采集关键性能指标（如 FP16 运算吞吐、显存带宽、TensorCore 利用率、INT8 推理延迟等），建立归一化的加权评分模型，对每块 GPU 给出训练性能分和推理性能分[22]。据此可自动判定该 GPU 更适合训练任务、推理任务或二者均衡，从而为调度决策提供一个直观的“类型标签”依据。这一机制使调度器能够“看懂”GPU差异，将合适的作业分配给合适的设备，大幅减少任务和资源的不匹配现象。这种类型感知的调度在现有系统中尚不多见，具有一定的创新性[3]。（2）公平性导向的学习型调度策略（先进性）: 在调度算法上，本课题将经典启发式策略与现代学习算法相结合，提出一种公平性导向的强化学习调度策略。首先引入 HRRN 响应比模型作为基础，以兼顾作业等待时间和估计运行时间，提高长期等待的小作业的调度优先级。然后利用图神经网络（GNN）对调度状态进行建模，将集群的任务队列、节点资源和vGPU使用情况编码成低维张量表示，再通过 Proximal Policy Optimization (PPO) 强化学习算法训练调度策略网络[26]。该策略网络在 HRRN 排序的基础上学习一个校正因子，根据不同负载模式实时调整对长等待任务与高负载节点的偏好程度。通过精心设计的奖励函数（综合平均等待时间、饥饿任务数等指标），引导策略朝着提高整体公平性的方向优化。本策略核心用于与FIFO等传统队列排队策略进行对比，突破了传统队列排队策略固定排序逻辑难以兼顾公平性和效率的问题，实现调度决策的动态自适应[24]。相比仅基于固定队列顺序的排队策略，RL 调度器能够在不同场景下自动权衡效率与公平，据文献报道在某些复杂环境下可取得显著性能提升[17]。因此，本课题的方法在调度策略层面具有较强的新颖性和研究价值。四、基于仿真分析的研究动机在本课题前期构建的多节点、多 vGPU 调度仿真环境中，我们实现并测试了 FIFO 等队列排队策略以及HRRN、随机等调度策略，重点考察HRRN强化学习模型与队列排队策略在 vGPU 分配场景下的等待时间、饥饿概率与公平性表现。实验结果显示：（1）在 vGPU 被细粒度切分、节点间显存剩余分布高度不均衡的情况下，传统 HRRN 的优势并未充分体现，而队列排队策略表现更差。HRRN 在 CPU 任务调度中能够显著降低长等待任务的饥饿概率，但在 vGPU 场景中，由于其调度依据仅依赖任务时间属性，而对底层 GPU 资源碎片结构缺乏感知，导致其优先级计算无法反映设备层面的可调度性，从而出现“响应比高但仍无法调度”的情况；队列排队策略则完全依赖任务到达顺序，对资源状态和任务特性均无感知，导致大量任务等待时间过长。（2）在高负载批次中，vGPU 的显存碎片与可用 slot 分布，使得 HRRN 的排队优势被抵消，队列排队策略性能进一步恶化。当某批次任务数较大、资源接近饱和时，仍然会出现大量任务即便具有较高响应比，也无可行节点满足其 vGPU slot 或显存需求；而队列排队策略由于缺乏灵活的排序调整机制，会导致系统拥堵，任务饥饿概率大幅上升。这说明传统 HRRN 及队列排队策略的排序逻辑并未考虑 GPU 物理结构（vGPU slot、显存碎片、GPU 间负载差异），其调度假设在vGPU场景下不再成立。（3）队列排队策略与传统调度策略在等待时间与饥饿任务数之间呈现固定的 trade-off，仅依赖手工公式或固定排队顺序已难以兼顾公平性和资源利用率。尽管 vGPU 调度的核心目标是尽可能提升 GPU 利用率，但在非抢占、资源碎片明显的条件下，提高利用率往往与减少饥饿任务或改善 slowdown 公平性相冲突。队列排队策略和传统调度策略均无法同时兼顾这些指标，导致在不同批次任务模式下表现波动较大。综上所述，队列排队策略及传统 HRRN 在 vGPU 场景中的公平性和调度有效性受到显著限制，需要一种“能够同时感知任务与 vGPU 资源结构”的可学习调度机制。基于此，本课题提出在 HRRN 基础上引入强化学习与图神经网络，构建HRRN强化学习模型，通过学习资源碎片模式、任务批次分布和设备选择结果，使其在 vGPU 环境下实现更优的等待时间–公平性折中，并通过与队列排队策略的系统对比，验证其优越性。（3）Kubernetes 插件级实现与系统集成（实用性）: 与很多只停留在仿真模拟或理论分析的研究不同，本课题非常重视方案的工程落地。我们将在 Kubernetes 原生调度框架上以插件形式实现整个调度算法，包括：调度前置的 GPU 类型探测 DaemonSet，负责收集并标记每个节点的 GPU 类型标签；调度器扩展插件，嵌入调度决策流程，实现自定义的打分函数和排序逻辑；以及与 Volcano、HAMi 的无缝对接，确保自研策略能应用于实际多租户环境[10]。整个实现将遵循 Kubernetes 调度器的扩展接口规范（Scheduling Framework），做到对现有平台“零侵入”兼容。如此设计的原型系统可直接部署在新华三 AMPHA 智算平台等生产环境中。平台运维人员可以以插件热插拔的方式评估和启用该调度策略，无需改变用户提交作业的方式，便于开展与现有队列排队策略的对比测试，具有很高的实用性[10]。（4）任务类型感知与混合调度支持（实用性）: 深度学习作业大致可分为训练任务和推理任务两大类，它们的资源需求和性能指标侧重有所不同[6]。训练通常追求计算吞吐，偏好算力强大的设备；推理则注重延迟，可能更看重显存带宽或可用缓存。本课题在调度算法中加入任务类型识别机制：通过对作业打标签（Training 或 Inference），并设计区分训练/推理的调度优先级公式[14]。例如，对推理任务可额外考虑其延迟敏感度提升优先级，对训练任务则考虑其对GPU计算能力的占用率[31]。结合上文提到的 GPU 类型标签，调度器在决策时会尽量匹配任务类型与 GPU 类型，例如将推理型任务调度到延迟低的 GPU，将训练型任务集中到计算型 GPU 上[23]。这一类型感知调度使混合负载场景下的资源分配更加合理，能够满足实际云平台同时处理训练和推理任务的需求，在与队列排队策略的对比中，更能凸显其在复杂场景下的实用价值[29]。综上，本课题聚焦的“异构 vGPU 性能感知 + 多租户公平调度”方向融合了前沿的新技术和实际的问题导向，具有明显的创新性与应用意义。一方面，我们引入类型识别、强化学习等新方法，构建HRRN强化学习模型，探索调度器设计的新思路；另一方面，我们强调落地实现，通过与传统队列排队策略的对比，服务于实际生产环境的需求。该研究的开展有望产出具有学术贡献和产业价值的成果。五、工作量评估- 样本任务建设（训练/推理任务组合）- vGPU 性能差异难以量化的问题，提出基于公开硬件规格与驱动层信息构建设备能力向量，并采用无监督聚类方式进行类型划分，为调度阶段提供可计算的资源类型先验。2. 探索公平性导向的 HRRN 增强型调度策略设计在传统 HRRN 排序模型基础上，引入资源状态感知与可学习的调度修正机制，探索在非抢占式 vGPU 场景下平衡任务等待时间与调度公平性的设计方法。3. 面向 Kubernetes 的插件化调度实现路径结合 Kubernetes 与 Volcano 调度框架，设计基于插件的调度扩展方式，使类型感知与公平性调度策略能够以低侵入方式集成到现有系统中。四、研究方法与技术路线一、拟采用的设计方法本课题拟采用“显卡性能采集 + 图神经网络建模 + 强化学习优化”的多层次、协同式资源调度设计方法，构建可泛化、可解释的智能调度系统。该方法融合微观资源能力识别、图结构建模与策略学习，涵盖“感知-建模-优化”全过程，在异构资源环境中实现更精细化的任务分配与资源调度。1. 性能采集驱动的 vGPU 类型识别机制传统 vGPU 调度策略普遍假设 GPU 资源同质，忽略不同型号 GPU/vGPU 在算力结构上的显著差异。本研究不依赖在线微基准测试，而是构建基于厂商公开规格与驱动层采集数据的“静态能力画像（Static GPU Capability Profiling）”。具体而言，通过 NVML、nvidia-smi 等接口获取每种 GPU 实例的核心硬件能力指标，包括：FP16/FP32 理论算力（TFLOPS）；INT8/TensorCore 吞吐（TOPS/TFLOPS）；SM 数量、TensorCore 支持情况；显存带宽（GB/s）与显存容量；vGPU Profile 对资源的限制。对上述指标进行归一化处理后构建设备能力特征向量，在该特征空间中采用无监督聚类模型（如高斯混合模型，GMM）自动发现 GPU 的结构性类型簇。通过对各簇中心在显存规模、带宽与算力分布等维度上的特征进行解释，将聚类结果后验映射为 Training-Oriented、Inference-Oriented 与 Balanced 三类类型标签，并通过 DaemonSet 周期性写入 Kubernetes 节点标签。2. 调度策略学习方法：基于 GNN 的 HRRN 增强与 PPO 优化调度评分策略以经典 HRRN 响应比公式为启发：本研究构建任务-节点-槽位的异构图结构，图中节点属性包含任务需求、等待时间、剩余资源量等，边连接反映任务与可调度节点之间的映射关系。状态编码采用 GNN（如 GraphSAGE、GAT）提取语义特征，作为调度评分模型输入。策略模型以 PPO（Proximal Policy Optimization）为基础，构建 Actor-Critic 框架，通过训练优化调度函数：奖励函数结合公平性指数、平均等待时间、资源利用率，促进调度策略在不同负载下实现性能-公平权衡。3. 插件式调度器集成与系统封装方法考虑系统可落地与易部署特性，采用模块解耦、插件组合方式构建完整调度系统：- 类型识别插件：DaemonSet 启动容器，周期性生成类型标签，写入 Node label；- 策略评分插件：实现 Volcano 的 NodeOrder 接口，将 GNN+PPO 模型封装为 REST/gRPC 服务独立部署；- 用户接口兼容：Pod YAML 中以注解方式指定任务类型（如 annotations: task-type=training），调度器根据标签匹配节点并执行打分排序。该架构可灵活部署于公有云/私有云/边缘平台，具备迁移性和可解释性，具备与新华三 Ampha 平台对接的潜力。二、技术路线与系统实现路径本课题实施路径分为五个阶段，形成完整从问题建模、策略训练、系统开发到实验评估的闭环。1. 资源特征提取与类型建模- 静态硬件能力采集（不运行任何测试负载）：通过部署在每个节点上的 DaemonSet，调用 NVML、nvidia-smi 等接口，采集 GPU 实例的关键硬件属性，包括：峰值算力（FP16、INT8 等）、显存容量、显存带宽、SM 数量、TensorCore 支持情况、以及 vGPU 对资源的限制。这些指标均为设备固有特性，不随运行任务变化，采集过程对业务无任何性能影响。- 构建设备能力向量并进行标准化处理：将采集到的硬件信息整合为统一的能力描述向量，包括计算能力、存储带宽能力、显存规模等多个维度。为消除不同量纲之间的差异，对所有指标进行标准化处理，使其能够在同一尺度下参与类型判断。- 基于无监督聚类的设备类型归纳：在标准化后的设备能力向量空间中，采用无监督聚类模型对 GPU 进行类型结构划分。该过程不依赖任何人工标签或任务运行数据，仅基于设备固有能力特征完成类型簇发现。通过对聚类结果的簇中心特征进行解释性分析，将不同类型簇映射为训练型、推理型与均衡型设备。此方法完全基于静态硬件信息，无需采集动态性能数据，分类过程稳定且透明。- 标签写入集群元数据并动态维护：将设备类型作为标签写入 Kubernetes 节点元数据。在节点重启、驱动更新或资源发生变化时，由 DaemonSet 自动重新采集硬件信息并更新标签，从而保持资源视图的实时性。调度器在运行阶段读取这些类型标签，使训练任务优先匹配训练型设备、推理任务优先匹配推理型设备，提升整体资源利用率与调度决策质量。2. 调度仿真与任务生成器- 搭建基于事件驱动的任务调度模拟器：采用Python实现事件驱动型仿真框架，核心包含任务生成、资源管理、调度执行、指标统计四大模块，支持自定义集群规模、vGPU配置、负载模式等参数，可精准复现真实集群的调度流程；- 模拟bursty/task-chain/workload skew等任务负载：设计多样化负载生成器，burst负载模拟任务突发到达（到达间隔服从泊松分布），task-chain负载模拟多任务依赖关系，workload skew负载模拟节点间负载不均衡（部分节点负载占比超70%），覆盖真实集群常见负载场景；- 实现HRRN/SJF/FCFS等baseline策略：基于仿真框架封装经典调度策略，FCFS按任务到达时间顺序调度，SJF优先调度估计运行时间最短的任务，HRRN结合等待时间与运行时间计算响应比，所有策略统一接口设计，便于后续与提出的GNN+PPO策略对比；- 评估指标包括avg_wait、slowdown、jain_fairness、资源碎片率等：实时统计任务平均等待时间（avg_wait）、任务减速比（slowdown=实际完成时间/估计运行时间）、Jain公平性指数（jain_fairness）、vGPU资源碎片率（未分配可用vGPU占比），生成多维度评估报告；3. PPO 策略网络训练- 图结构建模任务-资源状态：基于PyTorch Geometric框架构建任务-节点-槽位异构图，定义节点属性编码规则与边构建逻辑，采用GraphSAGE算法实现特征聚合，设置2层隐藏层（维度128→64），引入dropout机制（概率0.2）防止过拟合；- 构建Actor-Critic + GNN网络：Actor网络以GNN输出的特征向量为输入，通过全连接层输出各（任务-节点）组合的调度概率；Critic网络同样接收GNN特征，输出当前状态的价值评估值，双网络均采用ReLU激活函数，优化器选用Adam；- 奖励设计综合多维性能指标：奖励函数 = α×Jain指数 + β×(1-平均等待时间/阈值) + γ×资源利用率 - δ×饥饿任务数，其中α、β、γ、δ为动态权重，高负载场景下α、δ权重提升，低负载场景下β、γ权重提升，平衡不同优化目标；- 离线仿真训练策略，保存最佳模型：基于仿真平台生成10万+条训练数据，设置学习率3e-4、批次大小64、折扣因子0.95，训练迭代1000个epoch，每10个epoch验证一次，保存验证集性能最优的模型，采用ONNX格式导出便于后续部署；4. 插件开发与平台集成- 基于Go实现Volcano Plugin插件：遵循Volcano调度器插件开发规范，实现PreFilter、Score、NodeOrder等核心接口，插件负责解析Pod注解、查询节点标签、调用模型服务获取评分，支持配置调度阈值与权重，适配不同业务需求；- 策略模型封装为Python服务：基于FastAPI框架构建模型推理服务，暴露gRPC/REST接口，支持批量请求处理，服务内置请求限流（QPS≤1000）、超时重试（超时时间500ms）机制，打包为Docker镜像部署，支持水平扩展；- 任务与资源标签对齐，执行评分排序：调度器插件解析Pod的task-type注解，匹配节点vGPU类型标签，调用模型服务计算节点适配评分，按评分降序排序候选节点，优先将任务调度至类型匹配、负载较低的节点；- 若条件允许，集成Ampha平台测试：搭建与新华三Ampha平台一致的测试环境，配置Kubernetes+Volcano+HAMi架构，部署开发的插件与模型服务，提交训练、推理混合任务，验证系统在真实平台的兼容性与调度性能；5. 实验- 执行多组仿真实验对比策略效果：设计多变量对比实验，变量包括资源碎片率（20%/40%/60%/80%）、任务负载比例（训练:推理=3:7/5:5/7:3）、集群规模（3/5/10节点），每组实验重复5次，对比GNN+PPO与FCFS/SJF/HRRN策略的核心指标；- 分析策略间在不同负载下公平性与利用率趋势：采用Matplotlib/Seaborn绘制指标趋势图，分析不同负载场景下各策略的性能变化规律，重点探究高碎片、高负载场景下GNN+PPO策略的优势来源，通过统计检验（t检验）验证结果显著性；三、实践方案的可行性分析1. 工具链成熟、平台支持良好- 开发语言与平台：核心开发语言选用Python（模型训练、仿真平台）与Go（调度插件），集群环境基于Kubernetes构建，调度框架采用Volcano，适配主流云原生架构，降低开发与部署成本；- 框架工具：模型训练依赖PyTorch、PyTorch Geometric（GNN）、Ray RLlib（强化学习），性能采集采用CUDA
